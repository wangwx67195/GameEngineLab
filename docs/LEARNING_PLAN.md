## 1. 长期学习目标及“独立实现”的定义

### 1.1 核心目标（按优先顺序）

1. **基础编程能力**：自主组织 C++ 项目；能阅读报错、使用编译器/调试器、理解类型、作用域、值传递、引用、指针、内存、类、构建和调试。
2. **图形学基本功**：理解坐标、向量、矩阵、渲染管线、采样、插值、光栅化、深度、纹理、光照、帧缓冲、色彩空间、抗锯齿。
3. **算法与Shader实现能力**：推导并实现运动、几何判定、插值、变换、碰撞与渲染算法；使用Shader呈现结果。进阶视觉特效按兴趣穿插，不要求完成全部特效课程才能进入引擎主线。

### 3.1 用户已经理解的典型数学关系

- RGB 颜色（0～1）与 `vec4(R,G,B,A)`；Alpha 需要独立控制。
- 线性插值：`mix(A,B,t) = (1-t)A + tB`。
- 二维坐标归一化：`uv = fragCoord.xy / resolution`；如果按各方向独立归一化，用同一个半径计算会在非正方视口出现椭圆。
- 距离：`d = sqrt((x-cx)^2 + (y-cy)^2)`，GLSL `length(p-center)`。
- 宽高比 `aspect = W/H`：`p.x *= aspect`，或 `p.y *= H/W`；统一像素尺度亦可。
- `smoothstep(e0,e1,x)`：`e0<e1`；反方向用 `1.0 - smoothstep(...)`，颠倒参数不受保证，不一定编译报错。
- 圆环：独立的内外过渡阈值与 `ring_width`、`aa_width`；半径差与过渡宽度不能混为一谈。
- 周期运动：`r(t) = C + A sin(ωt)`，周期 `T=2π/ω`；`sin(2t)` 改频率，`2 sin(t)` 改振幅。
- 圆周运动：`x=cx+Rcos(t)`，`y=cy+Rsin(t)`，使用 `sin²t+cos²t=1` 证明。
- 运动更新：`x_new = x_old + v Δt`；不能使用每帧固定增加量来表示每秒速度。
- 整数除法：`7/2=3`，哪怕赋值给 double；需在除法前转换操作数，例如 `static_cast<double>(a)/b`。

### 3.2 已纠正或应反复强化的易错点

1. **GLSL 类型**：`1 - t_x` 在严格的 GLSL 编译环境可能产生整型/浮点型不匹配；习惯用 `1.0 - t_x`。
2. **预定义变量**：`gl_FragCoord` 是每个片段的位置，不是窗口尺寸；`u_resolution` 是应用提供的 uniform；`gl_FragColor` 为传统 GLSL 内置输出。
3. **渐变溢出**：`mix(A,B,t>1)` 是外插，不是报错或自动截断；归一化缓冲区可能截断最终通道。
4. **GLSL 向量构造**：`vec2(0.5,0.5)` 与 `(0.5,0.5)` 并非同一语义；不要误把逗号表达式当向量。
5. **浮点比较**：`d == radius` 不适合用于判断像素是否“位于圆周”。
6. **重复计算/无效赋值**：在之前练习中出现重复 `length(p)`、未使用的 `mask_2`/`mask_3` 与 `color=color`；引导优化但无需过度苛责。
7. **C++ 输入**：`int health; std::cin >> health;` 没有处理输入失败；需要学习检查 stream 状态。
8. **C++ 头文件**：误写 `<cstudio>`，正确是 `<cstdio>`；`std::printf`、`std::cout` 与 `namespace std` 已学习。
9. **时间直觉**：把 `delta_time` 从 1.0 改为 0.5，每次运动位移**减半**，12 次迭代总模拟时间**减半**，不应混淆循环次数与时间。
10. **函数值传递**：`void changeValue(int x){x=100;}` 不修改调用者的 `a`；这是早期教学提醒，后续引用/指针已有验收，不据此重开基础课。
11. **编译/运行区别**：工具宣称“已经实测”时，必须真的运行；Review 应区分“静态检查”“已编译”“已运行并验证输出”。

### 阶段 C 必须解释清楚的边界

- 顶点着色器→图元组装→光栅化→片段着色器→逐片段测试→帧缓冲。
- `gl_FragCoord` 与 NDC、UV、世界/观察/裁剪空间之间的区别。
- OpenGL 本身是图形 API，不是操作系统窗口库；GLFW 不负责整个渲染管线。
- GPU 并行与“一个 Fragment Shader 处理很多片段”的直觉；避免表述为“一段 C++ 每次调用 Shader 处理一个像素”。
- OpenGL Core Profile 的着色器版本、`in/out`、兼容性迁移；不要机械复用旧式 `gl_FragColor`。
- 不追求在第一版就封装巨大“Engine”框架；先完成最小可观察正确链路。

## 10. 阶段 G：把组件变成可用的游戏引擎（Lesson 66–80+）

| 模块 | 渐进实现顺序 | 最小验收 |

| 交互/工具 | ECS Inspector、Gizmo、摄像机控制、Debug Overlay | 用户无需改源码即可编辑部分场景参数 |
| 游戏运行 | 输入映射、状态机、UI、暂停/重启、关卡加载 | 可玩 2D 小游戏或 3D 探索 Demo |
| 可靠性 | 资源清理、错误处理、基本自动测试、Release 构建、文档 | 另一台 Ubuntu 机器根据 README 独立构建运行 |
| 发布 | 安装/打包、素材许可、日志/崩溃报告（基础） | 形成可交付的演示版本 |

建议完成两项作品：

1. **2D 小游戏**：至少包含角色控制、碰撞、界面、音效、关卡和退出/重启。
2. **3D 演示工程**：模型导入、场景、自由摄像机、光照、阴影、材质、后处理、属性调试面板。

**最终验收**（相对现实）：能从空仓库搭建独立 C++ 项目骨架，按自己设计的接口完成至少一个可玩的 Demo，并能解释每个模块如何与 GPU 渲染衔接。大型商业引擎的成熟度不作为毕业必要条件。

## 11. 阶段 H：选修与研究方向（按兴趣自主开启）

仅当基础完成、用户主动想进阶或课程项目确有需要时开启：

- **高级 Shader**：Compute Shader、粒子模拟、GPU 程序化纹理、Temporal AA、Motion Blur、屏幕空间反射、云和体积散射、实时水面、GPU 流体等。
- **现代渲染器**：Render Graph、Deferred Rendering、Clustered/Forward+、异步资源加载、实例化绘制、Bindless/现代资源绑定等。
- **Vulkan/底层 API**：显式同步、资源/队列/命令缓冲/管线；先具备 OpenGL 渲染管线直觉。
- **动画/人物**：骨骼动画、IK、蒙皮、物理布料、Morph Targets、动作重定向。
- **3D Gaussian Splatting（3DGS）/数字人**：作为可选插件式渲染后端或可视化模式；用户对此领域有研究兴趣，但**不能让它打断基础引擎的学习主线**。可研究 GPU 数据布局、排序/混合、动画驱动、OpenGL/Vulkan 互操作。
- **引擎工具链**：编辑器、素材导入管线、热重载、性能分析器、插件机制、多线程 Job System、跨平台抽象、自动化测试。

每个选修项目须有前置知识清单和一个小型验证性实验，避免出现“功能很酷，但代码全由 Agent 写”的情况。

## 12. 每节课的组织方式

完整课堂与API讲解契约见 [TEACHING_GUIDE.md](TEACHING_GUIDE.md)，状态与证据写入见 [PROGRESS_MAINTENANCE.md](PROGRESS_MAINTENANCE.md)。教学遵循“代码目标—原理—代码提示—API方法—实验—Review”，每个主题有学生亲写的可运行成果；图形阶段默认有画面/交互，当前工程过渡说明与运动可视化的衔接。

小测和变式用于验证核心理解，不机械凑题数；已通过部分不因课程重组重复验收。具体Review维度和已知薄弱点保留如下。

### 12.1 Code Review 标准

- **第一层：能否构建**——类型、语法、include、链接与依赖。
- **第二层：是否正确**——正常/边界/异常输入、浮点精度、坐标/单位、循环退出。
- **第三层：代码清晰度**——命名、重复计算、无用变量、缩进、职责分工。
- **第四层：工程问题**——资源所有权、可测试性、错误信息、版本兼容。
- 每次 Review 先明确“通过 / 基本通过 / 暂未通过”，并解释依据；禁止“没运行却说编译成功/所有测试通过”。
- 如果用户希望自己修复，**只给定位、原因、最小修改提示**；不要直接重写程序。对 `#include` 拼写等简单错误可明确指出修正形式。
- 一般使用 `g++ -std=c++17 -Wall -Wextra -pedantic ...`；到调试阶段可补 `-g` 和 sanitizers。执行程序时避免无限循环和修改重要文件。

### 12.2 针对学生已知薄弱点的额外要求

- 初学者代码同时出现多个新词时，一次拆开解释，不跳过分号、括号、作用域、类型转换、参数顺序。
- 重点用 **执行追踪表（变量每轮怎么变化）** 解释循环、值传递与条件判断。
- `std::cout`/`std::printf`：推荐现代 C++ 学习优先 `std::cout`；仍讲明 C 风格的兼容与 `%d`/`%f` 要求。
- `std::`：解释命名空间与 `::`；避免一开始把 `using namespace std;` 作为默认模板。
- 数学中清楚区分时间 `t`、角频率 `ω`、速度 `v`、时间步长 `Δt` 和帧编号 `frame`。
- Shader 中明确 CPU 传递 uniform 与 GPU 执行着色器的职责分界。

## 13. 课程组织、验收与记录制度

### 13.1 学习状态（每小节建议记录）

- `未开始`：尚未介绍。
- `已讲解`：课堂内容讲过，但没有收到实践证明。
- `练习中`：学生正在写代码。
- `待 Review`：学生已提交文件，尚未检查。
- `通过`：用户能解释并通过练习/测试。
- `需复习`：遇到误解，需小实验巩固。

### 13.2 验收不能仅以“程序跑了”为准

至少具备：

1. 用户能解释核心代码和基本数学；
2. 能在自己机器上运行或明确当前无法运行的原因；
3. 修改一个参数/输入还能预测结果；
4. 能描述至少一个边界/异常情况。

### 13.3 在主题里程碑进行复习

- 按主题里程碑复用旧知识进行短复习；已经能在项目中证明的能力不另加一轮形式化测验。
- 每阶段一个 mini-project，不以工程体量衡量，重点检查能否独立实现与口头解释。
- Agent 在代码 Review 或课程验收完成后自动记录到 `LEARNING_PROGRESS.md`，学生可随时补充或纠正。仅记录已证实的进度，部分练习通过不等于整课通过；此授权不包含修改练习源码或自动 commit/push。

### 13.4 Agent 会话切换时必须做的事

- 每次开始或继续章节学习都要核对进度，不限于新会话。跨设备先检查 Git 状态，按 2.3 节同步后重新读取文档；未实际同步时明确仅依据本地记录。
- 首先读三个文件：根目录 `AGENTS.md`、`docs/LEARNING_PROGRESS.md`、`docs/LEARNING_PLAN.md`，若专注教学再读 `game-engine-tutor/SKILL.md`。
- 先看 Git 工作树与课程目录，确定进度是不是已比文档更新；**文件与用户的最新口述优先**，不要覆盖现有源码。
- 首条回复应简短指出：当前掌握、未完成、准备继续哪课；**不必重新讲 01–08 所有知识**。
- 用户贴具体编译错误时先解决当前阻塞，别强行开始新课。
- 用户要求更换方向/跳课时尊重决定，同时告知先修知识的缺口，并设计短补课。

## 15. 学习路径的调整原则

- 以用户的长期目标为第一优先，而不是“课程表必须走完”。
- 如果用户对数学/SDF/视觉特效明显更有动力，可在 C++ 基础阶段插入短 Shader 项目；但任何进阶 Shader 都要解释旧 GLSL 与现代 OpenGL 的版本区别。
- 如果用户学 C++ 比预期快，可以合并重复概念；如果指针/内存/矩阵较难，则拆课、增加示意与测验。
- 不要求在固定时间内结束任何阶段；完成标准是能力，而不是总天数。
- 选用开源/免费资源，尊重许可证；第三方库源码不复制到本仓库作为学生作品。
- 一切工具或第三方资源的版本依赖，都要先核对实际环境再下结论。
