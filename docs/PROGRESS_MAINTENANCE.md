# 学习进度维护与跨设备交接

> 2026-10-27 整理；沿用用户此前关于自动记录的持续授权。

## 1. 读取与更新时机

- 每次开始或继续教学、Review 前，重读 [LEARNING_PROGRESS.md](LEARNING_PROGRESS.md)，核对对应课程文件和 `git status`。
- 已讲新内容、安排或调整任务后，记录“已讲解/待验收”；完成 Review、理论或整课验收后，自动记录实际结果，无需再次确认。
- 用户明确要求本轮不改文件时，尊重限制，只说明应记录的内容。
- 路线或教学规范发生变化时才更新计划/手册/入口；普通验收更新进度即可，不在每份教学文件里维护另一套当前状态。

## 2. 状态与证据

| 状态 | 使用条件 |
|---|---|
| 未开始 | 尚未讲授或安排 |
| 已讲解 | 已介绍概念与任务，尚无完成证明 |
| 练习中 | 学生确认开始编写 |
| 待Review | 学生提交了实际代码或答案，尚未检查 |
| 通过 | 对应必需代码/理论目标已得到验证 |
| 需复习 | 发现具体误解，需要定向巩固 |

同一主题可以“编程通过、理论待收尾”。部分小节通过不等于整课通过；学生请求下一课不等于已完成上一课。预期输出、旧测试、新测试分别标明，不为了日志完整捏造执行过程。

推荐证据表述：

- **静态判断**：阅读了哪些文件；根据规则预计什么行为；未执行。
- **实际验证**：构建命令或目标、必要环境、测试输入、实际输出/退出码及其与预期的比较。
- **Agent 临时实验**：说明是临时副本或独立样例，不代表学生亲做；不要写回学生源码。
- **学生口头回答**：只记录学生实际回答及教师补充，不能把教师解释算作学生已经独立掌握。
- **沿用既有证据**：注明此前哪次真实测试；没有改动且无新疑点时，无需为交接再次运行所有旧课。

## 3. 更新流程

1. 先读当前文档和实际文件，保留用户既有改动。
2. 更新顶部“当前状态”和相应课程任务清单，使“已完成 / 待完成 / 下一步”一致。
3. 按本次日期追加日志，保留历史；旧任务被新任务承接时写明对应关系，不把旧安排仍显示为当前待办。
4. 若只是补录历史，把它标为历史；不要用补录日期冒充授课日期。不确定的日期或状态明确标注。
5. 检查章节表、任务清单和最新日志是否矛盾；文档改动可用 `git diff --check` 检查格式。
6. 向学生简短报告记录结果与下一次入口；不自动暂存、提交或推送。

日志最小模板：

```md
### YYYY-MM-DD — Lesson NN：主题 / Review / 规划调整
- 状态：讲解、编程、理论与整课分别到哪里。
- 目标与已学原理：本次主题及其在引擎中的用途。
- 学生独立完成：实际文件、算法、回答；没有则明确未验收。
- 验证依据：静态判断 / 实际执行 / 沿用旧证据，及验证范围。
- 误区与反馈：具体错误及补充说明；可选整理不混作必修。
- 遗留与下一步：对应目录、任务、验收条件。
- 文档或路线调整：仅发生变化时填写，说明与既有进度的衔接。
```

## 4. 跨设备同步与路径

课程用仓库相对路径定位，例如 `lessons/14_multi_file/`。本机根目录实际是 `/home/wwx/projects/GameEngineLab`；另一台机器可以克隆到 `~/project/gameEngineLab`。目录大小写在 Linux 上有区别，Agent 先检查 `pwd`，不能自动重命名或搬动现有仓库。

离开设备时，由学生检查 diff，将本次代码、进度、变更的规则文档一起提交并 push。建议先选择具体路径暂存、检查暂存差异，再提交；不要机械执行 `git add .`。

在另一台设备上：

1. 先检查 `git status`、分支及远程配置。
2. 无未处理本地改动，且由用户操作或明确授权时，使用 `git pull --ff-only`。
3. 有改动或分支分叉时，先比较本地与远程内容并说明差异；不擅自覆盖、stash、reset、clean 或创建合并提交。
4. 同步后重读进度，核验实际源码，再继续教学。`origin/main` 可能只是本地缓存，未查询远程时不要声称远程实时最新。

授权自动维护进度不等于授权改练习源码、Git 提交/推送/拉取或搬动目录。当前 GitHub 仓库已存在，无需为路径拼写变化重新创建仓库。
